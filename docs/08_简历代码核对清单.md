## 关于「100% 合规率」：不建议写，三个代码级理由

**1. 主流水线的质检是纯大模型判断，没有确定性规则兜底**

`quality_reviewer.py` 只把文案拼进 Prompt 让 qwen-plus 返回 JSON，判定条件是：

```python
is_passed = (score >= 85.0) and (len(violations) == 0)
```

没有任何本地词表扫描，合规与否完全取决于模型这一次的输出。

**2. 解析失败会"放行"（fail-open）**

```python
except Exception:
    logger.warning("解析审核 JSON 失败，采用默认合格配置")
```

模型返回非 JSON（或多吐了一段解释文字导致 `json.loads` 失败）时，代码会退回 `score=96, passed=1, violations=[]`，即**默认判定合格**。这意味着"违规内容被放行"在代码路径上是存在的。

**3. 违禁词黑名单没有接入主流水线，且只有 5 个词**

`compliance_service.py` 里确实有一份黑名单：

```python
FORBIDDEN_WORDS = ["世界第一", "绝对有效", "100% cure", "best in the world", "cheapest"]
```

但它只被 `/compliance/check` 这个独立的实时筛查接口调用，工作流里的质检节点并没有用它。而且该接口里 LLM 调用的返回值被直接丢弃（`await` 了但没接结果），实际生效的只有这 5 个词的子串匹配——所以"双重检测"这个说法也不成立。

**4. Mock 模式下必然 100% 通过**

无 Key 时模型走 Mock，审核固定返回 `score=96, passed=1`。任何在无 Key 环境下的演示，都会呈现"100% 合规"的假象。

**结论**：这个数字既无法测（没有测试集、没有采样口径），也无法由代码保证（存在 fail-open 路径）。

### 替代写法（按风险从低到高）

- **最稳（推荐）**：不写数字，写机制 ——「质检不通过自动打回创意策划节点重写（上限 2 次），超限转人工，避免违规内容进入交付环节」
- **中等**：写双重检测的设计 ——「构建违禁词黑名单 + 大模型语义质检双重校验，命中红线词即判定不通过并触发回退」
- **要有数字**：必须限定口径并给出样本 ——「基于 N 条测试样本，违禁词拦截率 100%」，前提是你真的跑过这批样本

### 若要正当写出"100% 拦截"，需要先补两处代码

1. 把 `FORBIDDEN_WORDS` 硬扫接进 `quality_reviewer`，命中直接置 `is_passed=False`（不依赖模型）。
2. 把 fail-open 改为 **fail-closed**：解析失败时按"不通过 + 转人工"处理，而不是默认合格。

改完这两处，"违禁词命中即阻断"就是真的，简历可以写「基于黑名单的硬阻断 + 大模型语义质检双重校验」。

## 面试可能追问 & 建议答法

- **"为什么用 pgvector 不用 Milvus？"** → 数据量在百万级以内、与业务库同源可做同事务查询、少一套中间件运维；若未来向量量级上亿再考虑独立向量库。
- **"知识库文档不切分，长文档检索精度怎么保证？"** → 坦诚当前为整篇向量化，长文档会稀释语义，下一步计划引入滑动窗口 + overlap（这是真实待优化点，说出来比硬撑好）。
- **"多租户怎么防越权？"** → 全表 `tenant_id` + 仓储层强制条件 + 向量检索同样带租户过滤。
- **"重试 2 次怎么定的？"** → 平衡成本与收敛率；超限置 `failed` 转人工，避免无限循环烧 Token。
