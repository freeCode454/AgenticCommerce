# 架构风格与总体策略

## 2\.1 架构风格

本系统采用“分层架构 \+ 多智能体编排 \+ 事件驱动”的混合架构风格。

- 分层架构：后端采用 FastAPI 分层模式，划分为路由层、服务层、数据访问层与公共层，确保职责单一、依赖方向明确。

- 多智能体编排：核心业务由 LangGraph 状态图驱动的 7\-Agent 协作流水线完成。LangGraph 将智能体建模为状态图，节点是计算单元，边是路由逻辑，状态是贯穿全图的共享内存。

- 事件驱动：任务进度、Agent 节点状态、LLM 调用事件通过 WebSocket 实时推送至前端可观测工作台。

## 2\.2 多智能体架构选型依据

2026 年，智能体开发已从“Prompt \+ 工具调用”的简易编排演变为融合原生模型能力、持久化记忆、多智能体协作的系统工程。传统单体 Agent 存在三大致命缺陷：认知过载导致指令冲突、调试黑盒难以定位问题、成本失控。因此，本系统采用多智能体系统（MAS）架构，通过“路由 \+ 执行者”模式实现专业分工。

LangGraph 相较于传统 LangChain Chain 的核心优势在于：状态驱动、图结构、可中断、可恢复、可监控。系统采用 P\-E\-V（规划\-执行\-验证）循环的图结构变体，工作流从编排调度开始，经需求分析、创意策划、视觉设计，分支到图片/视频生成，最终由质量审核验证并决策路由。

## 2\.3 架构决策记录
| 编号 | 决策 | 理由 |
| :--- | :--- | :--- |
| ADR-001 | 采用 LangGraph StateGraph 而非 LangChain AgentExecutor | 需要条件路由、循环重试、状态持久化、节点级可观测 |
| ADR-002 | 采用 PostgreSQL + pgvector 统一存储关系数据与向量数据 | 减少组件数量，事务一致性，运维简单 |
| ADR-003 | 采用 WebSocket 而非 SSE 推送进度 | 支持双向通信，断线重连，多任务订阅 |
| ADR-004 | 采用 FastAPI 分层架构而非垂直切片 | 团队规模适中，横切关注点统一管理 |
| ADR-005 | 采用 OpenTelemetry 标准化埋点 + 自研工作台 | 避免厂商锁定，OTel 为 2026 年互操作标准 |
| ADR-006 | 采用 UUID varchar(36) 主键 | 便于分库分表，避免自增 ID 泄露业务量 |
| ADR-007 | 采用 Mock 降级策略 | 开发与演示环境不依赖外部 API Key |
| ADR-008 | 中间件只保留两个核心自研中间件 | 避免洋葱顺序失控、body 读取冲突、性能损耗 |
| ADR-009 | 认证与授权走依赖注入，不走全局中间件 | 登录、健康检查、文档不需要认证 |
| ADR-010 | 业务事务由服务层控制，不由中间件管理 | 事务边界属于业务语义 |

# 系统分层架构

## 3\.1 分层总览

系统整体分为六层，自上而下为：

```Plain Text
┌─────────────────────────────────────────────────────────────┐
│  第1层  前端展示层（Vue 3 + Vite + TypeScript）               │
│  管理后台 | SKU/任务 | 知识库 | 厂商配置 | Agent可观测工作台    │
├─────────────────────────────────────────────────────────────┤
│  第2层  接口层（FastAPI Routers + WebSocket）                 │
│  认证/租户 | SKU | 任务 | 知识库 | 厂商 | 资产 | 可观测 API     │
├─────────────────────────────────────────────────────────────┤
│  第3层  服务层（Services）                                    │
│  用户服务 | 任务服务 | 知识库服务 | 厂商服务 | 合规服务          │
├─────────────────────────────────────────────────────────────┤
│  第4层  智能体编排层（LangGraph 7-Agent Workflow）            │
│  Orchestrator → RequirementAnalyzer → CreativePlanner         │
│  → VisualDesigner → ImageGenerator/VideoGenerator             │
│  → QualityReviewer                                            │
├─────────────────────────────────────────────────────────────┤
│  第5层  数据访问层（Repositories + Clients）                  │
│  Repo层 | PG Client | Redis Client | MinIO Client | 厂商Client │
├─────────────────────────────────────────────────────────────┤
│  第6层  基础设施层                                            │
│  PostgreSQL + pgvector | Redis | MinIO | Docker | Nginx       │
└─────────────────────────────────────────────────────────────┘
```



## 3\.2 各层职责
| 层级 | 目录 | 职责 | 约束 |
| :--- | :--- | :--- | :--- |
| 前端展示层 | frontend/ | 页面渲染、用户交互、WebSocket 订阅 | 不直接调用数据库，不包含业务逻辑 |
| 接口层 | app/api/v1/ | 接收请求、参数校验、鉴权、响应格式化 | 不写业务逻辑，只做请求转发与响应封装 |
| 服务层 | app/services/ | 核心业务逻辑、事务管理、多组件协调 | 不直接操作数据库，通过 Repo 层访问数据 |
| 智能体编排层 | app/agent/ | LangGraph 工作流定义、Agent 节点实现、状态管理 | 不直接操作数据库，通过 Services 或 Clients 访问资源 |
| 数据访问层 | app/repositories/、app/clients/ | 数据库查询、缓存读写、文件存储、外部 API 调用 | 不包含业务规则，只做数据存取 |
| 基础设施层 | docker/、conf/ | 数据库、缓存、对象存储、容器编排 | — |

## 3\.3 依赖方向

```Plain Text
前端 → 接口层 → 服务层 → 数据访问层 → 基础设施
                  ↓
           智能体编排层 → 数据访问层
```

### 4\.2\.2 AgentState 状态定义

`AgentState` 是 LangGraph 状态图的共享状态，所有节点读取并更新其中字段。采用 `TypedDict` 定义，使用归约器（Reducer）控制并发更新行为。
| 字段 | 类型 | 归约器 | 说明 |
| :--- | :--- | :--- | :--- |
| product_info | dict | 覆盖 | 商品信息（品牌、类目、规格等） |
| generation_config | dict | 覆盖 | 生成配置（媒体类型、风格偏好等） |
| requirement_report | dict | 覆盖 | 需求分析报告 |
| creative_plan | dict | 覆盖 | 创意策划方案 |
| visual_design | dict | 覆盖 | 视觉设计方案 |
| generation_prompts | dict | 覆盖 | 生成提示词 |
| generated_images | list[dict] | add | 生成的图片列表 |
| generated_video | dict \| None | 覆盖 | 生成的视频 |
| quality_reports | list[dict] | add | 质量审核报告 |
| final_results | list[dict] | add | 最终通过的资产 |
| current_step | str | 覆盖 | 当前执行步骤 |
| errors | list[str] | add | 错误列表 |
| retry_count | int | 覆盖 | 重试计数 |
| completed_steps | list[str] | add | 已完成步骤列表 |

### 4\.2\.3 Agent 基类设计

所有 Agent 继承自统一 `BaseAgent` 抽象基类，确保一致的行为模式：

```Plain Text
BaseAgent (ABC)
├── __init__(model: str)
├── _build_prompt() -> ChatPromptTemplate   [抽象方法]
├── execute(state: dict) -> dict             [抽象方法]
└── _get_llm(temperature: float) -> LLM     [延迟加载]
```

职责分离：`_build_prompt()` 负责提示词模板构建，`execute()` 负责核心逻辑，`_get_llm()` 负责 LLM 实例延迟初始化。

### 4\.2\.4 条件路由设计

系统包含两处条件路由：

路由一：媒体类型路由（VisualDesigner 之后）
| 条件 | 目标节点 |
| :--- | :--- |
| media_type == "image" | ImageGenerator |
| media_type == "video" | VideoGenerator |
| media_type == "mixed" | ImageGenerator（可扩展并行视频） |

路由二：质量审核路由（QualityReviewer 之后）
| 条件 | 目标节点 | 说明 |
| :--- | :--- | :--- |
| passed == true | END | 审核通过，输出资产 |
| passed == false 且 retry_count < max_retries | CreativePlanner | 重做创意方案 |
| passed == false 且 retry_count >= max_retries | END | 终止，标记失败，提示人工介入 |

条件边基于当前 State 的实时值动态决定目标节点，支持分支、循环重试、异常回滚。

### 4\.2\.5 Checkpoint 与持久化

工作流使用 Checkpoint 机制保存执行状态：

- 开发环境：`MemorySaver`（内存级，快速迭代）

- 生产环境：`PostgresSaver`（持久化，支持断点恢复）

每个 `thread_id` 对应一个独立的执行会话，支持 `interrupt()` 人工介入与 `resume()` 恢复执行。

```

该管道使用 RAG 架构的双层检索设计：L1 缓存摘要层快速命中，L2 向量检索 \+ 重排序精准召回。

### 4\.3\.2 知识分类与向量化
| 知识分类 | doc_type | 检索触发 Agent | 用途 |
| :--- | :--- | :--- | :--- |

### 4\.3\.3 向量存储策略

- 向量维度：1024（千问 text\-embedding\-v4 与 BGE\-large\-zh 一致）

- 索引类型：IVFFlat（默认，lists=100）或 HNSW（高并发场景）

- 租户隔离：向量检索时强制附加 `tenant_id` 过滤条件

## 5\.3 RAG 检索流程（以 RequirementAnalyzer 为例）

    │

    ORDER BY embedding <=> query_vec

    │
    ▼

    │
    ▼

```

## 6\.2 核心数据实体关系

```Plain Text
Tenant ─┬─ User
        ├─ Provider
        ├─ KnowledgeBaseDoc ── KnowledgeChunk
        ├─ SKU ─┬─ Task ─┬─ Copy(文案)
        │        │        ├─ Asset(素材资产)
        │        │        ├─ ComplianceReport(合规报告)
        │        │        └─ TaskNodeRun(节点执行记录)
        │        └─ Listing (二期)
        └─ Batch ─ Task
```

## 6\.3 数据隔离策略

采用“请求级 \+ 数据库级”双重隔离：
| 隔离层级 | 实现方式 |
| :--- | :--- |
| 请求级 | 所有 API 请求通过 JWT 解析出 tenant_id，注入请求上下文 |
| 服务级 | Service 层所有查询自动附加 tenant_id 过滤条件 |
| 数据级 | 所有业务表包含 tenant_id 字段，建立组合索引 |
| 向量级 | RAG 检索时强制附加 tenant_id 过滤 |
| WebSocket 级 | 订阅鉴权，禁止跨租户订阅 |

多租户 SaaS 解决方案通常为每个租户使用分区键（如 `/TenantId`）实现逻辑隔离。本系统采用共享数据库 \+ 租户 ID 分区键模式，在成本与隔离之间取得平衡。

## 6\.4 数据流转

```Plain Text
写入路径:
用户请求 → 接口层(tenant_id注入) → 服务层(业务逻辑) → Repo层(参数化查询) → PostgreSQL

读取路径:
用户请求 → 接口层(tenant_id注入) → 服务层(业务逻辑) → Repo层(tenant_id过滤) → PostgreSQL → 返回
```

## 6\.5 缓存策略
| 缓存项 | 存储 | TTL | 更新策略 |
| :--- | :--- | :--- | :--- |
| 用户会话 | Redis | 24h | JWT 过期同步 |
| 租户配置 | Redis | 1h | 配置变更时主动失效 |
| 知识库分块 | PostgreSQL | — | 文档变更时重新向量化 |
| 任务进度 | Redis | 任务完成后 1h | 实时更新 |
| WebSocket 事件 | Redis | 1h | 事件推送后保留 |

## 8\.2 环境配置策略

系统支持两种运行模式：

1. 开发环境：仅基础设施（PostgreSQL、Redis、MinIO）容器化，后端与前端在宿主机本地运行，利用热重载提升开发效率。基础设施数据直接映射到项目 `data/` 目录，方便查看。

开发环境与生产环境的差异仅在于运行位置与网络地址，业务代码完全一致，通过环境变量 `POSTGRES_HOST`、`REDIS_URL`、`MINIO_ENDPOINT` 区分。

# 横切关注点

## 9\.1 错误处理
| 层级 | 策略 |
| :--- | :--- |
| 接口层 | 统一异常处理器，返回标准错误格式 {code, message} |
| 服务层 | 业务异常捕获，事务回滚，记录错误日志 |
| Agent 节点 | 单节点失败不阻断其他节点，错误写入 errors 列表 |
| 外部调用 | 超时控制 + 指数退避重试 + 熔断降级 |
| 任务级 | 单任务失败不影响其他任务，支持单独重试 |

## 9\.2 日志架构设计

本系统采用“分层日志 \+ 全链路追踪”的设计，日志不依赖单一中间件，而是按职责拆分到不同层级。
| 日志类型 | 记录内容 | 承载组件 | 输出格式 |
| :--- | :--- | :--- | :--- |
| 访问日志 | method、path、status、elapsed、client_ip | RequestContextMiddleware + logging | JSON |
| 业务日志 | 业务动作、参数、结果 | 服务层（Service） | JSON，含 trace_id |
| Agent 日志 | 节点名、输入、输出、耗时、Token、费用 | LangGraph 节点 + WebSocket | JSON，含 task_id/node_name |
| 审计日志 | 用户、动作、目标、结果 | 服务层 + 事件总线（异步） | JSON，保留 ≥30 天 |
| 错误日志 | 异常堆栈、错误码、上下文 | 全局异常处理器 + 服务层 | JSON，含 stack_trace |
| 可观测日志 | Trace、Metrics、Span | OpenTelemetry 自动插桩 | OTel 协议 |

全链路追踪机制：

1. `RequestContextMiddleware` 在请求入口生成 `request_id` 和 `trace_id`，写入 `contextvars`。

2. 服务层、Repo 层、Agent 节点通过 `logging` 框架自动携带 `trace_id`。

3. LangGraph 节点执行时，读取 `trace_id` 并写入 `TaskNodeRun` 表。

4. WebSocket 推送事件时，携带 `trace_id`，前端工作台按 `trace_id` 关联展示。

5. OpenTelemetry 自动插桩，生成 Span，贯穿 HTTP → Service → Agent → LLM。

日志规范：

- 所有日志统一 JSON 格式，便于 ELK / Loki 采集。

- 日志中禁止输出密码、API Key、完整请求体等敏感信息。

- 访问日志、业务日志、Agent 日志默认保留 7 天；审计日志保留 ≥30 天。

- 日志级别：DEBUG（开发）、INFO（生产）、WARN、ERROR。

- 关键路径（任务创建、工作流执行、合规阻断）必须打 INFO 及以上日志。

# FastAPI 中间件设计

## 10\.1 设计结论

本系统采用“核心中间件 \+ 内置中间件 \+ 依赖注入 \+ 服务层下沉”的组合策略。

自研核心中间件只保留 2 个，其余能力分别由内置中间件、依赖注入、全局异常处理器、服务层和 OpenTelemetry 承接。

## 10\.2 横切关注点归属映射
| 实现载体 | 包含能力 | 数量 |
| :--- | :--- | :--- |
| 自研中间件 | RequestContextMiddleware（request_id/trace_id、租户/用户上下文预解析、访问日志基础字段）<br>GlobalGuardMiddleware（安全响应头、限流、请求体大小限制、可选配额与幂等） | 2 个 |
| 内置中间件 | CORSMiddleware、GZipMiddleware、TrustedHostMiddleware、HTTPSRedirectMiddleware | 4 个 |
| 依赖注入 | 认证（Depends(get_current_user)）、角色权限（Depends(require_role(...))） | 2 项 |
| 全局异常处理器 | 统一错误响应 | 1 项 |
| 服务层 | 审计日志、数据库事务、可选配额与幂等 | 3 项 |
| OpenTelemetry | Metrics / Tracing | 1 项 |
| WebSocket 端点依赖 | WebSocket 鉴权 | 1 项 |

## 10\.3 核心中间件职责

### 10\.3\.1 RequestContextMiddleware

- 读取或生成 `X-Request-ID`；

- 生成 `trace_id`，用于 OpenTelemetry 与 Agent 可观测；

- 尝试解析 JWT，写入 `tenant_id`、`user_id`、`role`；

- 同时写入 `request.state` 与 `contextvars`；

- 响应头返回 `X-Request-ID`；

- 只做“预解析”，不强制阻断，强制认证交给依赖注入。

### 10\.3\.2 GlobalGuardMiddleware

- 添加安全响应头；

- 基于 Redis 做限流；

- 检查 `Content-Length`，限制请求体大小；

- 可选：租户配额检查；

- 可选：`Idempotency-Key` 幂等控制；

- 超限返回 429、413 或 402。

## 10\.4 中间件执行顺序

从外到内建议为：

1. ServerErrorMiddleware

2. HTTPSRedirectMiddleware

3. TrustedHostMiddleware

4. CORSMiddleware

5. RequestContextMiddleware

6. GlobalGuardMiddleware

7. GZipMiddleware

8. ExceptionMiddleware

9. Router → 依赖 → 路由函数

注意：Starlette 中间件遵循“洋葱模型”。`app.add_middleware()` 是向栈内插入，后添加的中间件位于外层，在请求阶段最先执行。因此，代码中添加顺序与请求执行顺序相反。建议按“从内到外”的逻辑添加：先添加希望最晚接触请求的中间件，最后添加希望最先接触请求的中间件。

```Python
from fastapi import FastAPI
from starlette.middleware.cors import CORSMiddleware
from starlette.middleware.gzip import GZipMiddleware
from starlette.middleware.trustedhost import TrustedHostMiddleware
from starlette.middleware.httpsredirect import HTTPSRedirectMiddleware

app = FastAPI(title="AgenticCommerce")

# 按从内到外添加
app.add_middleware(GZipMiddleware, minimum_size=1000)  # 最内层，最后处理请求
app.add_middleware(GlobalGuardMiddleware)              # 中间层
app.add_middleware(RequestContextMiddleware)           # 最外层，最先拦截请求

app.add_middleware(
    CORSMiddleware,
    allow_origins=settings.CORS_ORIGINS,
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)

app.add_middleware(
    TrustedHostMiddleware,
    allowed_hosts=settings.TRUSTED_HOSTS,
)

if settings.ENV == "prod":
    app.add_middleware(HTTPSRedirectMiddleware)
```

## 10\.5 配置项
| 配置项 | 说明 | 默认 |
| :--- | :--- | :--- |
| CORS_ORIGINS | 允许跨域来源 | 前端域名 |
| TRUSTED_HOSTS | 允许 Host | 生产域名 |
| RATE_LIMIT_PER_MINUTE | 每分钟限流 | 600 |
| BODY_MAX_SIZE | 请求体最大字节 | 10MB |
| QUOTA_ENABLED | 是否启用配额 | FALSE |
| IDEMPOTENCY_ENABLED | 是否启用幂等 | FALSE |
| OTEL_ENABLED | OpenTelemetry 开关 | TRUE |

## 10\.6 验收标准

- 每个请求有唯一 `request_id`，响应头返回 `X-Request-ID`。

- `tenant_id`、`user_id`、`trace_id` 在服务层、Repo 层、Agent 节点可读取。

- 限流生效，超限返回 429；请求体超限返回 413。

- 安全响应头、CORS、TrustedHost 生效。

- 认证与角色权限由依赖注入完成，不由中间件完成。

- 统一错误响应由全局异常处理器完成。

- WebSocket 单独鉴权，禁止跨租户订阅。

- OpenTelemetry Trace 贯穿 HTTP → Service → Agent → LLM。

- 中间件不破坏流式响应、文件下载与 OpenAPI 文档。
